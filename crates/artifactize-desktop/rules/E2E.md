# Desktop end-to-end rules

When the suite passes locally, it should very likely pass on the other platforms too; to that end, whatever differs between platforms is handled in one place. Rules state outcomes; mechanisms belong in code comments. The TEST- rules of project-rules/DEV-CODING.md and project-rules/DEV-PLATFORM.md apply. Reference: https://v2.tauri.app/develop/tests/webdriver/ and https://webdriver.io/docs/desktop-testing/tauri/.

- E2E-WDIO-SERVICE: the suite runs on WebdriverIO with @wdio/tauri-service and the embedded WebDriver provider on every OS, and they alone start and stop the app. A window the product launches is its child: the suite only attaches an observation session and confirms it exits.
- E2E-PROVIDER-UPSTREAM: the vendored provider is the unmodified upstream release (lint-checked); test-only native devices live in the desktop crate's own code.
- E2E-TEST-BUILD-ONLY: the WebdriverIO plugins exist only in the E2E test build, the only build the suite runs.
- E2E-REAL-APP: cases drive the built app through its real UI, never by invoking app commands, mocking IPC or scripting the page to change product state. Fixtures control only declared external inputs; a window-frame action the page cannot reach (close, focus) uses Tauri's window API.
- E2E-INPUT: input reaches the app only through WebDriver commands, the test-only text-input device (WebView-engine text and editing APIs only) or the one helper that delivers the DOM events a user's input would where the provider lacks them. Nothing injects OS-level input events or calls app code.
- E2E-PLATFORM: whatever differs between operating systems is handled in the platform layer (`e2e/platform.ts`); other files use its portable functions and never name or branch on an OS (lint-enforced). It holds OS differences only: domain fixtures (stand-in programs, browser fakes) and portable I/O live outside it.
- E2E-ISOLATED: each scenario is valid alone and in any order, on its own repository, state and environment, never the user's live ones. A once-per-machine resource (fixed port, clipboard, foreground window) is declared and used by one app instance at a time; no other lock hides interference.
- E2E-OWNED-FIXTURES: a fixture belongs to one app instance and is released only once that app and everything it launched are confirmed ended; an unconfirmed end is a failure that keeps the fixture's files.
- E2E-CAUSAL-OUTCOMES: a case waits for what the window shows as the result of its own action, not a fixed sleep, an accepted command or text that already matched. What the window cannot show (the app exiting) is observed outside it.
- E2E-EXPLICIT-FAILURE: a missing prerequisite, a setup or cleanup failure, or a cancelled or incomplete run is a failure, never a skip or a pass.
- E2E-COVERAGE: a journey is covered when a scenario performs its action by a visible path and checks its key visible outcome once; finer assertions, variants and keyboard shortcuts are optional. Pasting counts as entering text unless the journey needs the clipboard.
