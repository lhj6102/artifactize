# Desktop end-to-end rules

How the desktop app's end-to-end suite is written and run. Their purpose: when the E2E suite
passes locally, it should very likely pass on the other platforms too; to that end, everything
that differs between platforms is handled in one place. Their reference is Tauri's WebDriver
guide (https://v2.tauri.app/develop/tests/webdriver/) and the WebdriverIO Tauri service docs
(https://webdriver.io/docs/desktop-testing/tauri/). The shared TEST- rules of
project-rules/DEV-CODING.md apply as well.

- E2E-WDIO-SERVICE: the suite runs on the WebdriverIO test runner with @wdio/tauri-service and the embedded WebDriver provider (tauri-plugin-wdio-webdriver), the same provider on Linux, Windows and macOS. The runner and service own app launch, WebDriver provisioning and shutdown, with capability-specific endpoints declared only in runner configuration. Specs and helpers do not spawn or kill the app or a WebDriver server, and do not wrap or re-wire the service's launcher lifecycle. The one exception is an app instance the product itself launches, such as the window the Human graph tool opens: it stays the product's child, not one the suite starts, and the suite only attaches an observation session to it through runner configuration (its exit is confirmed as E2E-OWNED-FIXTURES says). That is not a helper spawning the app. When a journey's expected outcome is the app quitting, once its exit is observed (E2E-CAUSAL-OUTCOMES) the spec marks that WebDriver session ended through one shared helper; this is the only session bookkeeping specs may do. On Linux, every run of the whole runner, from a terminal or a graphical desktop, runs under dbus-run-session and xvfb-run -a with X11, and the platform layer verifies that display and bus are that private session's, never the user's desktop.
- E2E-INPUT: input reaches the app only through WebDriver commands or through the suite's native text-input device, which uses only the WebView engine's own text-input API: WebKit's input-method context on Linux, the WKWebView's NSTextInputClient on macOS, and WebView2's DevTools Protocol Input domain on Windows. Copy and paste use each engine's editing commands: WebKit's Copy/Paste on Linux, the WKWebView responder's copy:/paste: on macOS, and on Windows, where WebView2 offers no other editing action, the DevTools Protocol's Input.dispatchKeyEvent with a fixed payload of type keyDown carrying only the command Copy or Paste. The engine runs that command; the page sees a keyDown with no key, code, modifier or virtual-key code, which is permitted, since no user key or shortcut reaches it. Any other call of that method, one with a key, code, modifier or virtual-key code, without such a command, or with a payload built at run time, is a raw key event and remains forbidden. Neither the suite, its WebDriver provider nor the device synthesizes or injects OS-level events, such as NSApp sendEvent, constructed GdkEvents through gtk_widget_event, SendInput or keybd_event. Such events behave differently per OS and cannot be verified on Linux. A guarantee that is the app's own logic, such as ignoring shortcuts while an input method composes, is verified at the page, through the event fields the app reads (isComposing, keyCode 229), while a native composition is active. Where the WebDriver provider lacks a standard key or pointer event, such as PageUp/PageDown or pointerdown/pointerup, one input helper in the suite dispatches exactly the DOM events that the WebDriver action would deliver to the focused or targeted element, the same way the provider dispatches its own input. The provider-gap helper also supplies omitted browser defaults: Tab's sequential focus navigation, a focused button's activation by Enter or Space, the native caret of a click on selectable text, and an option click's WebDriver selection steps, only when the page has not prevented the input. It never calls app code, sets app state directly, or produces events a user's input could not.
- E2E-PROVIDER-UPSTREAM: `vendor/tauri-plugin-wdio-webdriver` holds the provider's upstream source, unmodified, as `ui/e2e/provider-upstream.json` records the release file by file. The provider's own build writes one file into that folder, its permission reference under `permissions/autogenerated/`; that build output is not source and is the only file besides the release's. The suite's lint compares the folder with the record byte for byte. Test-only native devices the suite needs, such as the input-method device, live in the desktop crate's own evaluated code, and the platform layer reaches them through one portable function.
- E2E-PLATFORM: e2e/platform.ts is the suite's only platform layer and the first place to look for an OS difference. Only it names an operating system, reads or changes the process environment, builds native paths, touches the file system, starts, observes or stops processes, opens sockets, or chooses OS-specific values such as executable names, OS user directories and the primary shortcut modifier. It exposes portable functions that behave the same on Linux, Windows and macOS: native paths flow only into file system and process calls, including a path that a started program opens itself (a Tauri build input in its configuration variable); a path written into a file, a declaration or an argument template, or compared with what the app shows, uses '/', except a path given to a setting that also accepts a URL, which keeps a native spelling that cannot read as a URL. An interrupt reaches a child runner the way the OS delivers it, through the platform layer, so the child can still shut its app down. The platform layer also confirms the end of the whole process tree of a build or fixture program it starts (a Unix process group, a Windows Job Object) before that tree's inputs are released, on completion and on cancellation; starts a tool through an entry point the OS launches directly, with an argument vector (a Windows `.cmd` shim is resolved to its program); and reserves WebDriver ports outside the OS's ephemeral port range, releasing each listener just before the service binds it while keeping the reservation claimed until the service has started. A process counts as ended once it has exited, reaped or not (a Unix zombie has ended; Windows has no such state). Every other spec, fixture, helper, fixture program and runner configuration file uses those functions instead. The suite's lint enforces the import, process-value and OS-literal restrictions mechanically; beyond them, platform.ts returns normalized values rather than leaking OS-shaped ones, and no other file reproduces OS-dependent behavior by other means.
- E2E-TEST-BUILD-ONLY: the suite builds and runs only the E2E test build, selected by one Cargo feature and the matching frontend build, and gets the WebdriverIO plugins (their Rust crates, capability permissions and the frontend import) only through that selection.
- E2E-REAL-APP: drive the built test app through its real UI. Do not invoke the app's own commands (the E2E-only text-input command that E2E-INPUT's device uses is not one), mock Tauri commands or intercept invoke, and do not use browser.tauri.execute or page script to perform product actions or change app state; IPC mocking belongs in the component tests. Input dispatched as E2E-INPUT allows is not a product action. The one exception is an action on the OS window frame that the page cannot reach, such as closing or focusing the window: it goes through Tauri's own public window API, for example close(), which raises the same CloseRequested event as the frame's close button, or setFocus(). Only the E2E-only capability permits it, and any OS-specific handling lives in the platform layer. Fixtures may control declared external inputs (repository contents, agent or backend stand-ins, network services), not the product behavior under test.
- E2E-ISOLATED: each spec is valid on its own and in any order by establishing its starting state through the real UI and declared external inputs. Specs of one capability may share the service-owned app lifetime, not rely on another spec's actions or leftovers. A companion window the product launches belongs to the instance that launched it and inherits that instance's inputs by design. Separate capabilities/instances may run in parallel with disjoint repository/state directories, environment inputs and endpoints. The user's live environment stays untouched. A product-fixed or desktop-wide resource that cannot be given per instance and that only some capabilities use (such as a fixed callback port, or the macOS general pasteboard of native copy and paste) is used by one capability only, declared in the runner configuration. Where an OS service cannot be redirected per instance, such as the Windows default URL handler, the runner configuration confines that platform's run to a disposable CI machine and fails explicitly anywhere else. Do not add global locks or serialization to hide interference. The one exception is an OS resource that exists once per desktop and that every instance needs, such as the Windows foreground window, without which WebView2 gives a page no focus events: the platform layer declares it, and only on that platform the runner starts its instances one at a time. A window setting an engine needs to keep rendering while another window covers it, such as WKWebView's background throttling on macOS, is likewise the platform layer's.
- E2E-OWNED-FIXTURES: a fixture belongs to an app instance/capability, not to a spec or a worker: setup scoped to that instance creates it, and the matching teardown releases it only after the runner and service have ended that app instance, after any companion window that instance launched has closed and its process has ended, which the suite confirms, and after the app's web engine helper processes have released the fixture's data, with a bounded wait that fails when they do not. The same holds for an external fixture program the app launches (an opener, a browser stand-in) and its descendants. An end that cannot be confirmed is a cleanup failure (E2E-EXPLICIT-FAILURE): teardown keeps the fixture's files for diagnosis while still closing the fixture's servers and jobs. Teardown may run after the WebdriverIO runner returns; worker/session hooks must not delete fixtures still used by the launcher-owned app.
- E2E-CAUSAL-OUTCOMES: in the real app, an outcome the window can show is what the window shows once the case's own action has completed (an outcome it cannot show, such as the app's own exit, is observed through the platform layer): wait with WebdriverIO's waitFor*/waitUntil on that user-visible result; a fixed sleep, a dispatch count, text that matched before the action, a merely accepted WebDriver command and a transient render are not substitutes, and a read-only probe that a forbidden action did not happen must also be shown to observe a real successful one. Assert what the window shows, not mounted counts.
- E2E-EXPLICIT-FAILURE: a missing platform prerequisite, a setup or cleanup failure, a cancelled or incomplete run is a failure, never skipped coverage or a passing exit.
