# Desktop end-to-end rules

When the suite passes on one machine, it should very likely pass on the other operating systems too. Rules state outcomes; mechanisms belong in code comments. The TEST- rules of project-rules/DEV-CODING.md and project-rules/DEV-PLATFORM.md apply. Reference: https://v2.tauri.app/develop/tests/webdriver/ and https://webdriver.io/docs/desktop-testing/tauri/.

- E2E-INPUT: the suite runs on WebdriverIO with @wdio/tauri-service and the vendored embedded WebDriver provider on every OS, and they start and stop the app; the provider is the unmodified upstream release, and test-only native devices live in the desktop crate's own code. Input reaches the app only through WebDriver commands, the test-only text-input device (WebView-engine text and editing APIs only) and the one input helper that does for the user what the provider lacks, such as WebDriver's own option-click steps. Nothing injects OS-level input events or calls app code (lint-checked).
- E2E-TEST-BUILD-ONLY: the WebdriverIO plugins exist only in the E2E test build, the only build the suite runs.
- E2E-REAL-APP: cases drive the built app through its real UI and wait for what the window shows (text, roles, attributes) as the result of their own action, never for a fixed time or for text that already matched. They never invoke app commands, mock IPC, script the page to change product state or read its internals (page globals, injected observers, drawn shapes); pixels are read only where the app paints on a canvas. Fixtures control only declared external inputs; a window-frame action the page cannot reach (close, focus) uses Tauri's window API, and what the window cannot show (the app exiting) is observed outside it.
- E2E-PLATFORM: whatever differs between operating systems is handled in the platform layer (`e2e/platform.ts`), which holds OS differences only; other files never name or branch on an OS (lint-checked). Every OS uses the same fakes and seams wherever it can, so no OS has a path of its own.
- E2E-ISOLATED: each scenario is valid alone and in any order, on its own repository, state and environment, never the user's, and runs on a developer's machine as well as on a CI runner. A once-per-machine resource (a fixed port, the clipboard) is used by one app at a time. Teardown closes what the scenario started and deletes its files, retrying while the OS still holds them.
- E2E-EXPLICIT-FAILURE: a missing prerequisite, a setup or cleanup failure, or a cancelled or incomplete run is a failure, never a skip or a pass.
- E2E-COVERAGE: a journey (J- id) is covered when a scenario performs its action by a visible path and checks its key visible outcome once; one scenario may cover several journeys and names the ones it covers. Finer assertions, variants, keyboard shortcuts, colours, icon shapes and error edge cases are optional, and belong in component tests when they matter. Pasting counts as entering text unless the journey needs the clipboard.
