The AI-native collaboration layer for one-of-a-kind teammates and their agents.

Split a project into Artifacts, each with its own evals: tests, LLM reviews, human sign-offs and derived dependency checks. Every teammate, human or agent, works their own way, and integrating their work never pays for the same review twice.

Why I built it

Solo got fast with AI. Teamwork should too.

Building games with AI, working alone got fast, but working with others still felt like hitting a wall. There had to be a sweet spot between traditional development and AI-native work. So I looked for a way for every teammate, human or agent, to keep their own style and still add up to one coherent result, and I structured the project around evaluation.

Artifactize is that collaboration layer: it splits a project into modules that each carry their own evaluation criteria, so everyone can work their way, and it cuts the evaluation cost wasted during integration.

01An idea

It starts with an idea.

A few notes on what to build. Nothing is declared yet, so there is nothing to review and no verdict to reuse.

At this point there is one note, the Idea: not yet an Artifact, with no fingerprint.

02Artifacts

The idea and a spec become Artifacts.

A folder with index.artf is an Artifact; a sidecar such as spec.md.artf declares a single file. Both use TOML and require a name. The default fingerprint is artifactsum: it hashes the Artifact's own files, excluding *.artf declarations. fingerprint = false disables reuse. Here an Agent checks that the Spec is complete.

name = "spec"
# fingerprint omitted: artifactsum is the default

Now there are two Artifacts, Idea and Spec, each with a short fingerprint, and one Agent eval that reviews the Spec alone; it executes once.

03Evals

Code arrives, and evals connect the parts.

An eval reviews one Artifact, alone or against others: every other Artifact it names becomes a dependency of that review, drawn as an edge. An Agent eval reviews the code against the Spec, another the Spec against the Idea, and Alice signs off the Spec itself as a Human eval. A dependency eval can instead derive readiness from other Artifacts' required evals: it runs nothing, is never cached or published, and appears separately as derived work.

payload.instruction = "Review {code} against {spec}."

A derived readiness condition uses the same eval table, with no payload or verdict schema. artifactize verify player/ready includes the required dependency evals automatically. Missing evidence gives WAIT_DEPENDENCY; RED evidence gives BLOCKED. This optional eval is not part of the story's execution counts.

[evals.ready]
title = "Movement and art are ready"
profile = { kind = "dependency", depends_on = ["player-movement", "hero-art"] }

Code joins Idea and Spec. Agent evals review Code against the Spec and the Spec against the Idea, and Alice signs off the Spec alone in a Human eval. All three execute once; the Spec's completeness review is reused.

04Tests and style

Tests run as runtime evals, and a style sheet reviews the code.

Inside Code, a runtime eval runs the tests: any command can review an Artifact, and exit code 0 is GREEN. A coding-style sheet becomes an Artifact too: an Agent eval reviews the source against it, and Alice signs the sheet off. The four earlier verdicts still hold, so they are reused.

profile = { kind = "runtime", command = "cargo", args = ["test"] }

Code now holds src and tests. Three evals execute: src against tests (runtime), src against the Style sheet (Agent), and Alice's sign-off of the Style sheet alone (Human). The four earlier evals are reused.

05Modules

The code splits into modules.

src becomes three child Artifacts, core, cli and api, each with its own fingerprint, tests and style review; api, the public interface, also gets a Human sign-off. From now on a change to one module re-reviews that module and what depends on it, not the whole codebase. Tags such as tags = ["type:code"] label Artifacts in status, graph and monitor output; they change neither relations nor reuse keys.

src is now three modules, core, cli and api, each reviewed against tests and the Style sheet, and api has a Human sign-off by Alice. Those seven execute, and so does Code's review, because its children changed; the other four are reused.

06Beyond code

A website and docs pages join the graph.

The docs pages are reviewed against the api module, and their build runs as a runtime eval of its own. The website's runtime evals check its links into the docs and run its code samples against api, and Dana, a designer, signs the website off. More Artifacts now depend on the code, so a code change has more to re-review.

Docs pages and Website join. Five new evals execute: the docs against api, the docs' own build, the website against the docs and against api, and Dana's sign-off of the website alone.

07A change

Change one module, and only what depends on it runs again.

Edit api and its fingerprint changes. Its own evals go stale and run first, its Human review included: Alice signs off the new api once. The evals that depend on api wait for them, then run: the code's review against the Spec, the docs pages and the website samples. The other eleven verdicts, the Spec's and the website's sign-offs among them, are reused.

$ artifactize status
…
Verify actions: will execute 3, will reuse 11, wait 3, blocked 0

api's fingerprint changes. Its tests and style review run, its Human review waits for Alice's sign-off, then the three evals that depend on api run. Six evals execute, one of them a sign-off; eleven are reused.

08It keeps growing

New Artifacts and relations keep arriving.

A sync module joins the code, a brand guide arrives to review the website against, and the docs pages start covering the CLI. Each addition runs its own evals once; every verdict already earned stays reused.

sync and a Brand guide join, and the docs gain an eval against cli. Four new evals execute; seventeen are reused.

09Work in parallel

Split the work across copies of one repository.

Alice changes the docs in her clone, Bob changes api in a worktree and Carol changes cli in another. Each runs verify in their own copy and publishes the verdicts to the team's artifactize server. It is one project with the same Artifacts, and paths are not part of the reuse key, so whatever a change did not touch is reused across the copies. Bob's api change needs Alice's sign-off once, in his copy.

$ artifactize remote login https://reviews.example/

The project now exists as three copies of the same repository around the review store: app · alice/docs, app · bob/api and app · carol/cli. In each copy the changed Artifact and the evals that depend on it run again, fourteen in all, one of them the sign-off of Bob's api; the other 49 are reused. Each copy publishes its verdicts to the store and reuses verdicts from it.

10Merge and CI

CI runs only what the merge made new, and each sign-off happens once.

The copies merge into main. CI runs verify --all with a read-only token: it reuses the verdicts the copies already earned from the store, the sign-off of Bob's api included, and executes only evals whose inputs are new after the merge, those that see two people's changes at once: the code's review against the Spec and the docs' reviews of api and cli. No Human review is asked for again.

# CI on main: store URL and read token in the env
$ artifactize verify --all
Summary: executed 3 (runtime 0, agent 3, human 0), reused 18 (runtime 7, agent 7, human 4)

The copies merge back into app · main, so api and cli take their new fingerprints. The evals the copies already reviewed, api's sign-off included, are reused from the store; the three that see two changes at once execute. CI reads verdicts from the store: executed 3, reused 18.

Get started

Try it in five minutes.

Artifactize is open source under the Apache License 2.0. Install it with one command, no Rust toolchain needed; the quick start then reviews an example project with no model or API key.

# Linux or WSL 2 (x86_64, aarch64): installs to ~/.local/bin, no sudo
$ curl -fsSL https://artifactize.dev/install.sh | sh
$ artifactize --version
# Windows x86_64 in PowerShell (experimental): installs to
# %LOCALAPPDATA%\Programs\artifactize and adds it to your PATH, no admin
PS> irm https://artifactize.dev/install.ps1 | iex
PS> artifactize --version

macOS support is coming. Follow its progress in issue #111.

Upgrading to 0.9: declarations move to TOML .artf, families are removed, state schema 6 requires a new state, and reuse-key v2 reuses no earlier verdict. Every executable eval needs one new review, Human sign-offs included. Upgrade instructions.
