Each step below describes the project and what the decorative graphic beside it shows.

01An idea

It starts with an idea.

A few notes on what to build. Nothing is declared yet, so there is nothing to review and no verdict to reuse.

In the graphic: one dashed node, Idea, with no fingerprint.

02Artifacts

The idea and a spec become Artifacts.

A folder with an artifactize.json is an Artifact: a doc, a spec, a module, a website, a style sheet. Each declares a fingerprint, what its reviews depend on; the built-in one hashes the folder's own files. An eval can review one Artifact on its own: here an Agent checks that the Spec is complete.

"fingerprint": {}

In the graphic: two Artifacts, Idea and Spec, each showing a short fingerprint. An Agent eval loops on the Spec, reviewing it alone, and executes once.

03Evals

Code arrives, and evals connect the parts.

An eval reviews one Artifact, alone or against others: every other Artifact it names becomes a dependency of that review, drawn as an edge. An Agent eval reviews the code against the Spec, another the Spec against the Idea, and Alice signs off the Spec itself as a Human eval.

"instruction": "Review {code} against {spec}."

In the graphic: Code appears below Idea and Spec. Agent eval edges run from Code to Spec and from Spec to Idea, and a Human eval loops on the Spec, marked with its reviewer, Alice. All three execute once; the Spec's completeness review is reused.

04Tests and style

Tests run as runtime evals, and a style sheet reviews the code.

Inside Code, a runtime eval runs the tests: any command can review an Artifact, and exit code 0 is GREEN. A coding-style sheet becomes an Artifact too: an Agent eval reviews the source against it, and Alice signs the sheet off. The four earlier verdicts still hold, so they are reused.

"kind": "runtime",
"command": "cargo", "args": ["test"]

In the graphic: Code opens into a frame holding src and tests. A runtime eval joins src to tests, an Agent eval joins src to the Style sheet, and a Human eval loops on the Style sheet, reviewed by Alice; all three execute. The four earlier evals are reused.

05Modules

The code splits into modules.

src becomes three child Artifacts, core, cli and api, each with its own fingerprint, tests and style review; api, the public interface, also gets a Human sign-off. From now on a change to one module re-reviews that module and what depends on it, not the whole codebase.

In the graphic: src splits into core, cli and api inside the Code frame. Each module gets a runtime eval against tests and an Agent eval against the Style sheet, and a Human eval loops on api, reviewed by Alice. Those seven execute, and so does Code's review, because its children changed; the other four are reused.

06Beyond code

A website and docs pages join the graph.

The docs pages are reviewed against the api module, and their build runs as a runtime eval of its own. The website's runtime evals check its links into the docs and run its code samples against api, and Dana, a designer, signs the website off. More Artifacts now depend on the code, so a code change has more to re-review.

In the graphic: Docs pages and Website appear below the code. Five new evals execute: the docs against api, the docs' build (a loop on Docs pages), the website against the docs and against api, and Dana's sign-off of the website (a loop on Website).

07A change

Change one module, and only what depends on it runs again.

Edit api and its fingerprint changes. Its own evals go stale and run first, its Human review included: Alice signs off the new api once. The evals that depend on api wait for them, then run: the code's review against the Spec, the docs pages and the website samples. The other eleven verdicts, the Spec's and the website's sign-offs among them, are reused.

$ artifactize status
…
Verify actions: will execute 3, will reuse 11, wait 3, blocked 0

In the graphic: api's fingerprint changes and a ripple spreads from it. api's tests and style review turn stale and run, its Human review waits for Alice's sign-off, then the three evals that depend on api run. Six evals execute, one of them a sign-off; eleven stay reused.

08It keeps growing

New Artifacts and relations keep arriving.

A sync module joins the code, a brand guide arrives to review the website against, and the docs pages start covering the CLI. Each addition runs its own evals once; every verdict already earned stays reused.

In the graphic: sync joins the modules, Brand guide joins the website, and the docs gain an eval against cli. Four new evals execute; seventeen are reused.

09Work in parallel

Split the work across copies of one repository.

Alice changes the docs in her clone, Bob changes api in a worktree and Carol changes cli in another. Each runs verify in their own copy and publishes the verdicts to the team's artifactize server. It is one project with the same Artifacts, and paths are not part of the reuse key, so whatever a change did not touch is reused across the copies. Bob's api change needs Alice's sign-off once, in his copy.

$ artifactize remote login https://reviews.example/

In the graphic: the project zooms out into three copies of the same repository around the review store: app · alice/docs, app · bob/api and app · carol/cli. In each copy the changed Artifact and the evals that depend on it turn stale and run, fourteen in all, one of them the sign-off of Bob's api; the other 49 are reused. Verdicts flow between each copy and the store.

10Merge and CI

CI runs only what the merge made new, and each sign-off happens once.

The copies merge into main. CI runs verify --all with a read-only token: it reuses the verdicts the copies already earned from the store, the sign-off of Bob's api included, and executes only evals whose inputs are new after the merge, those that see two people's changes at once: the code's review against the Spec and the docs' reviews of api and cli. No Human review is asked for again.

# CI on main: store URL and read token in the env
$ artifactize verify --all
Summary: executed 3 (runtime 0, agent 3, human 0), reused 18 (runtime 7, agent 7, human 4)

In the graphic: the copies merge back into app · main, so api and cli take their new fingerprints. Their evals turn stale; those the copies already reviewed, api's sign-off included, come back reused from the store, and the three that see two changes at once execute. A CI lane reads verdicts from the store: executed 3, reused 18.

Get started

Try it in five minutes.

Artifactize is open source under the Apache License 2.0. Install the latest release from crates.io with Cargo on Linux or WSL 2; the quick start then reviews an example project with no model or API key.

# Linux or WSL 2, with a Rust toolchain and a C compiler
$ cargo install artifactize --locked
$ artifactize --version
artifactize 0.5.1
