Build together on an Artifact Graph.

Bring your way of working to the team. Pick a part, show what is ready, and build on your teammates’ reviewed work. An Artifact is a piece of your project: code, writing, a design or an image. The graph connects those pieces and their checks—tests, AI reviews and a person’s approval. Artifactize calls these checks evals, and reuses their results when their inputs haven’t changed.

Why I built it

Solo got fast with AI. Teamwork should too.

Building games with AI made solo work faster. I wanted teammates and their assistants to work their own way too, without repeating reviews every time we brought our work together.

Each part keeps its own checks. The team shares results that still apply, and reviews the changes that need attention.

Each step below describes the project at that point; the animated graphic beside it shows the same.

01An idea

It starts with an idea.

A few notes on what to build. Nothing is declared yet, so there is nothing to review and no verdict to reuse.

At this point there is one note, the Idea: not yet an Artifact, with no fingerprint.

02Artifacts

The plan and specification become Artifacts.

Choose the pieces you want to review separately. Here, a plan and a specification become Artifacts, and an AI checks whether the specification is complete.

Now there are two Artifacts, Idea and Spec, each with a short fingerprint, and one Agent eval that reviews the Spec alone; it executes once.

03Evals

Code arrives, and checks connect the parts.

A check can compare one piece with another. Here, AI reviews compare the code with its specification, and Alice reviews the specification before approving it.

Code joins Idea and Spec. Agent evals review Code against the Spec and the Spec against the Idea, and Alice signs off the Spec alone in a Human eval. All three execute once; the Spec's completeness review is reused.

04Tests and style

Tests and a style review check the code.

Tests run automatically. An AI checks the code against a style guide, while Alice approves the guide. Earlier results still apply and are reused.

Code now holds src and tests. Three evals execute: src against tests (runtime), src against the Style sheet (Agent), and Alice's sign-off of the Style sheet alone (Human). The four earlier evals are reused.

05Modules

The code splits into modules.

Split larger pieces into smaller ones, each with its own checks. A change can then be reviewed where it matters instead of restarting every review.

src is now three modules, core, cli and api, each reviewed against tests and the Style sheet, and api has a Human sign-off by Alice. Those seven execute, and so does Code's review, because its children changed; the other four are reused.

06Beyond code

A website and docs pages join the graph.

Writing and design belong in the same project. Check the documentation against the public interface, test the website, and ask a designer to approve it.

Docs pages and Website join. Five new evals execute: the docs against api, the docs' own build, the website against the docs and against api, and Dana's sign-off of the website alone.

07A change

Change one module, and only what depends on it runs again.

Change the public interface. Its checks and the checks that use it run again; unrelated results and unchanged approvals are reused.

api's fingerprint changes. Its tests and style review run, its Human review waits for Alice's sign-off, then the three evals that depend on api run. Six evals execute, one of them a sign-off; eleven are reused.

08It keeps growing

New Artifacts and relations keep arriving.

Add new work and new connections as the project grows. New checks run once, while earlier results remain reusable when their inputs still match.

sync and a Brand guide join, and the docs gain an eval against cli. Four new evals execute; seventeen are reused.

09Work in parallel

Work on your own copy of the project.

Alice, Bob and Carol work on their own copies of the project. A shared review store lets each teammate reuse results earned in the other copies.

The project now exists as three copies of the same repository around the review store: app · alice/docs, app · bob/api and app · carol/cli. In each copy the changed Artifact and the evals that depend on it run again, fourteen in all, one of them the sign-off of Bob's api; the other 49 are reused. Each copy publishes its verdicts to the store and reuses verdicts from it.

10Merge and CI

Bring changes together and check only what is new.

Bring the changes together. Automatic checks reuse the results from each teammate’s copy and review only the new combinations created by the merge.

The copies merge back into app · main, so api and cli take their new fingerprints. The evals the copies already reviewed, api's sign-off included, are reused from the store; the three that see two changes at once execute. CI reads verdicts from the store: executed 3, reused 18.
